### T9. AI 虚拟桌面（预想阶段，**不开工**）
想法：利用 Windows 自带的多屏/虚拟桌面能力，给 AI 单独一块虚拟桌面，
人用真实桌面、AI 用虚拟桌面，彻底隔离。
**状态：评审中 → 初步结论「不推荐」（2026-11-05）**

`doc-critic` 的技术评审（依据 Windows API 语义，未逐条实测）：
1. **Win10 虚拟桌面不隔离**：多桌面共用同一 window station / desktop 对象，只是 shell 的可见性分组。
   非活动桌面 DWM 不合成 → **截图空白**；`SendInput` 只进**活动输入桌面** → **AI 在隐藏桌面上干不了活**。
2. **虚拟显示器（IddCx）给零隔离**：多屏只是扩展桌面，焦点/输入/剪贴板全共享。
   代价是内核驱动 + EV 证书 + 微软签名 + 管理员安装；驱动 bugcheck = 开机黑屏。
3. **剪贴板是 window station 属性**：同会话所有桌面共享，只有换会话能隔离。
4. 换会话是唯一真隔离，但要把 DSH 宿主一起搬走 → 用户看不见、ESC 刹车失效，**与"人能看见能停"的产品前提冲突**。

**关键反转（采纳）**：
> 「不渲染」⇒ 不需要合成器 ⇒ **也不需要桌面**。
> 最终形态是"没有桌面，只有窗口句柄"。

**替代方案（成本 1~2 天，推荐）**：
把"不干扰"从**几何约束**升级为**权限约束** —— AI 只准操作已绑定的窗口，越界即拒绝并写理由。
项目已有基础：bound window、`dump`、intercept 四模式。

**技术调研交叉验证（`gpu-minimap`，2026-11-05）**：
- `CreateDesktop` 与 `Win+Ctrl+D`：**都不可用**（同会话只有 1 个可见桌面且收输入；
  非交互窗口站的桌面不允许切可见；DDA 要求 active output）
- **虚拟显示器（VDD）**：抓得到画面（它是真 DXGI output，可直接复用现有 `gpucap`），
  但**没有输入/焦点隔离**——焦点、Alt-Tab、指针仍是全局的。5~10 轮，需装签名驱动 + 管理员
- **独立会话**：本机 `fSingleSessionPerUser=1`、RDP 关闭，二次登录会踢掉控制台。不可行
- **Hyper-V / Sandbox**：本机未装，**C 盘只剩 16.3GB**，无 GPU-P → 不可行
- **重要更正**：用户以为"不渲染所以便宜"——但**装了虚拟显示器后 DWM 照样合成**，
  Windows 没有"停渲染某块屏"的开关。能省的只有"不抓帧"，不是"不渲染"。
  所以"不渲染"这个优势**只在不建桌面时才成立**（即 critic 的解读）。

**待办小修**：拖拽模式下 40×40 热区会吃掉点击（占屏 0.077%）——改成"按需激活"即可，
不需要为此上内核驱动。

**结论（两条独立评审一致）**：
- **真隔离**（互不干扰的最高形态）在本机**做不到**：唯一给真隔离的 VM 路线磁盘不够
- **可达的近似**有两条，都只解决一半：
  - VDD：解决"AI 窗口不压在你屏幕上"，不解决"抢焦点/抢输入"（5~10 轮 + 装驱动）
  - 权限隔离：解决"AI 不能碰你没绑定的窗口"，不解决"窗口压在你屏幕上"（1~2 天）
- **待用户确认**：他要的"虚拟桌面"是**隔离**，还是**多一块屏放 AI 的窗口**？
  这决定选哪条；若只是后者，VDD 可行但要接受装内核驱动的风险

| 滚动条 | **两条都能用真鼠标拖**（`ScrollBar`/`scroll_drag`），3px 细条 + 向内容侧 4px 抓取区 | 细条好看但点不中；抓取区不能吃掉边框热区 |

## 三、工作纪律（用户明确要求）

**用户的明确指示（重要）**：验证不要过频——反复跑全套测试本身就耗性能、耗时间。
- 小改动：编译 + 一次冒烟即可，**不要每次都把 5 套测试全跑一遍**
- 大改动（跨进程/渲染/布局）：才跑全量
- 报告里写清"这次验了什么、没验什么"，不要为了显得严谨而重复验证

**产品目的（决定了取舍方向）**：AI 鼠标的核心是**人机操作分离、互不干扰**。
所以优先级是：不抢焦点 > 不挡人操作 > 视觉好看 > 功能丰富。

**每个任务开工前先给「开工单」**，等用户点头再写代码：

```

预算：改动行数上限 / 预计几轮 / 上下文预算
```

## 五、渲染重建构想（**已搁置**，用户状态好时再议）

用户明确要求：本轮不动渲染，先把 T2（面板窗口化）做完。

下面是已经构思好的重建方案，**只存档，不开工**。到时候从"P0-prep 像素基线"开始。

### 目标架构
```
scene（显示列表/控件树）—— 几何唯一真相，绘制与命中共用
        │  Backend trait
   ┌────┴─────┐
 CPU 后端      GPU 后端
 tiny-skia     D3D11 + DirectComposition
 → UpdateLayeredWindow
```

### 阶段与门槛
| 阶段 | 内容 | 门槛 |
|---|---|---|
| P0-prep | golden image 比对工具 + 采集当前基线 | 连续两次渲染差异=0（证明确定性） |
| P0 | 抽出 scene 层，不改行为 | 与基线**逐像素一致** |
| P1 | CPU 后端换 tiny-skia | 逐像素一致；光标一帧 <400μs |
| **P2** | **DirectComposition 原型（一个小方窗）** | 透明✅ 穿透✅ 不抢焦点✅ —— **止损点** |
| P3 | GPU 后端接进同一 scene | 与 P1 一致；设备丢失能降级 |
| P4 | 单进程承载多光标 | N 只光标 CPU 线性度改善 |
| P5 | 删除旧 Canvas/GDI | 35/35 + 实机脚本 + 二进制变小 |

### 绝不能犯的错
1. **三个 Win32 硬约束每阶段重测**：逐像素透明 / 点击穿透 / 不抢焦点
2. **预乘 alpha**：alpha=0 的像素 RGB 必须为 0，否则黑边白边
3. **透明度只在最后一趟应用**：`alpha=255` 有快路径、`alpha=250` 掉进逐像素混合（面板底 270μs vs 2641μs，9.8 倍）
4. **文字自备 fallback**：`msyh.ttc` 缺 `✕`(U+2715)；规矩是**符号一律矢量画**，只有正文走字体
5. **主循环帧契约**：`continue` 前必须 sleep；stale 命令只跳命令不跳帧
6. **构建纪律**：`touch -d "2030-01-01"` + md5 校验，否则 cargo 假装成功
7. **降级链要真跑过**：真的让它失败一次，看它退到下一级还能出画面
8. **一次只改一个维度**：功能和渲染不许同阶段改

### 已知数据（tiny-skia 探针，已提交 f216c40）
- 光标 1893μs → 338μs（5.6×）；面板 27205μs → 3559μs（6.9×）
- swizzle 只有 compose 的 1/10~1/18，吃不掉收益
- 二进制 **+0 字节**（tiny-skia 已由 resvg 拉进依赖树）
- 真 UpdateLayeredWindow 抓屏比对 86400/86400 像素误差 ≤2/255，无黑边白边
