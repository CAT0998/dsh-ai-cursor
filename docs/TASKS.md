## 二、已定决策（不要再反复）

| 决策 | 结论 | 理由 |
|---|---|---|
| 用游戏引擎（Urho3D/Unity/Bevy）包一层 | **否决** | 透明+穿透+不抢焦点仍要手写 Win32；引擎体积大且不为"一个精灵"优化；小地图已证明裸 D3D11 够用 |
| 渲染 GPU 化的路线 | **先 CPU 优化（T3），再验证 DirectComposition（T4）** | 小地图实测：瓶颈在 `compose`+`UpdateLayeredWindow`，不在抓屏 |
| 菜单缩放 | **删除** | 与"窗口缩放"概念重复，且实现成了"整体放大字体+间距"，是错误理解 |
| 面板数量 | **只保留一个** | 多面板与"箭头切换编辑对象"冲突 |
| 窗口拉宽 | **内容固定、右侧留白**（方案 A） | 方案 B（内容重排）要重写整套布局计算 |
| 横向滚动条 | **仅在窗口窄于 452 时出现** | 内容宽度是固定设计值 |
| 文档"每次改动存一份图" | **否决** | git 已存事实；存意图声明无法验证，revert 退不回去；中位改动 46 行，画图成本远超收益 |
| "严格按逻辑图写代码" | **否决** | 同一图对应多种合法实现，图选不出对错 |

## 三、工作纪律（用户明确要求）

**每个任务开工前先给「开工单」**，等用户点头再写代码：

```
【开工单】
目标：一句话
预算：改动行数上限 / 预计几轮 / 上下文预算
验收：怎么证明成功（具体到命令、数字、截图）
影响面：动哪些区块、哪些共享状态、哪些跨进程通道
不做：明确排除项
留的余地：为将来预留什么
```

**反面例子（本次会话真实发生过的补丁链）**：
- 加「保存/删除」按钮 → 提示文字压住按钮 → 补一刀挪位置
- 加「旋转」滑杆 → `art_rot` 与协议命令撞名 → 补一刀改名
- 加栏头 → 只发给第一只光标 → 补一刀"发给全部"
- **让「图案」默认展开 → 面板 1139 高 → 「预设」掉到任务栏下点不到 → 补一刀做滚动**

**规矩**：
1. 有分支的地方按结构写（表驱动），不按当下这一条写
2. 新增状态字段前先想清"谁写/何时写/谁读/失败怎么办"
3. 布局改动先算总高预算
4. **一次只改一个维度**，功能与布局分开提交
