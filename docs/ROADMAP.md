### P3 层级锚点 —— ⚠️ z 序未生效；已改用「绑定窗口 + 位置计算」的方案
**2026-10-29 新方案（按建议改成镜像/绑定思路，已实测通过）**：
不移动窗口 z 序，而是把光标**绑定到一个窗口**，位置由该窗口 rect 算术得出：
```
ai_mouse_layer { mode:"window", hwnd:"0x2C1660" }
  → layer=window Chrome_WidgetWin_1, rect=[312,110,1296,828]
光标 (900,520) → anchor_rel [588,410] inside=true
光标 (200,100) → anchor_rel [-112,-10] inside=false
```
数值与算术完全吻合。`GetWindowRect` 是缓存读，不会像读标题那样卡住浮层。
绑定不改变目标窗口的 z 序 / 位置 / 大小 / 焦点。配合 `window_capture` 即可把一个
窗口单独渲染出来给 AI 看。

**仍未解决**：真正的"把光标压在某个窗口下面"（z 序插入）在这一版 Windows 上没生效，
已放弃这条路。
让 AI 鼠标在**各应用窗口之间自由切换**，且**绝不打扰其他窗口**（不改 z 序、不移动、不缩放、不抢焦点）。
- 锚点模式：`topmost` / `above:<窗口>` / `below:<窗口>` / `desktop`
- 面板显示当前锚点窗口的标题、类名、进程、z 序号
- `SetWinEventHook` 跟随锚点窗口移动/最小化
- **只改自己窗口的 z 序**，对其他窗口只读不写

**2026-10-29 实测状态（第二轮，仍失败）**：又加了两步仍无效：
1. 每次锚定后回读 `GWL_EXSTYLE` 写进 `status.layer_topmost`；
2. 低频率看门狗（400ms）重复锚定，防重绘把窗口顶回去；
3. 先显式 `SetWindowPos(HWND_NOTOPMOST)` 降级，再插入到锚点位置。
结果：`below:0x2C1660` 之后 `EnumWindows` 里我们的窗口仍是 index 2、锚点 index 3，
**依旧在锚点之前**。下一步要看 `status.layer_topmost` 的真值，以及 `SetWindowPos`
的返回值/GetLastError——现在的代码把返回值丢掉了（`let _ =`），这是最该改的地方。

**第一轮记录**：`ai_mouse_layer` 能收下命令、能用 `GetClassNameW` 解析锚点、
`ai_mouse_windows_at` 能正确列出窗口栈（修复了跨进程读标题导致浮层挂死的问题）。
但设成 `below:<窗口>` 之后，`WS_EX_TOPMOST` 仍然留在我们的两个窗口上，枚举出来的
z 序里光标依旧排在锚点**之前**——也就是说 **`apply_layer` 的效果没有落地**。

下一步排查方向（按可能性排序）：
1. `SetWindowPos(hwnd, anchor, …)` 是否真的被执行（在 apply 处加一行回读

### P6 设计要点（原始需求）
> 新需求（2026-10-29）：让 AI 的**子代理也能使用这个插件**——每个代理智能体都有自己的 AI 鼠标，各自用不同的配置，并且可以**自定义预设**。

设计要点（待细化）：
- 现在是一进程一只光标、一套状态。要变成**多光标**：一个浮层进程管理 N 个光标窗口，每个带 `agentId`。
- 工具按调用者的 agent 身份路由：`ai_mouse_*` 作用于**调用它的那个 agent 的光标**，而不是全局那只。
- 每只光标一套配置（造型 / 颜色 / 尺寸 / 透明度 / 徽章 / 层级 / 图案槽位），来源优先级：**预设 < 按 agent 覆盖 < 运行时工具调用**。
- **预设（preset）**：命名的一组配置，可保存/加载/复制；新子代理按预设自动分配外观（例如按 agent 名 hash 出颜色，避免两只光标撞色）。
- 面板需要从"这只光标"变成"光标列表 + 当前选中"，或按 agent 分页。
- 权限等级要**按 agent 独立**，不能一个子代理拉低所有光标。

### P9 线程与渲染优化
- **多核**：现在浮层是单线程（主消息循环 + 一个 stdin 读线程）。渲染、协议解析、精灵解码（GIF/SVG 解码最重）应分到不同线程；优先把**解码**和**合成**从主循环挪走。
- **别再让 CPU 扛渲染**：现在每帧是 GDI 逐像素合成（SS=2 超采样），CPU 占用高。
  方案：`Direct2D` + `DXGI` 交换链，或 `Direct3D 11` 纹理上传播放。
  **但先测再决定**：需要先量出真实 CPU 占用（空闲 / 动图播放 / 拖动三种场景），
  如果空闲时 CPU 接近 0，那"优化"的重点应放在动画时的峰值而不是全盘重写。

### 面板/停靠站 缩放：必须改成参数化布局（2026-10-30 定位）

**已排除**：拉伸成品图。证据来自 `Canvas::compose` 自身：

```rust
let stride_big = self.w * self.ss;      // 画布固定尺寸
for oy in 0..h { for ox in 0..w {
    let i = (row + (ox*ss + sx)*4);     // 按索引取样 = 裁剪，不是等比映射
    let o = ((oy * self.w + ox)*4);     // 写出步长仍是 self.w
}}
```

`w/h` 只是循环边界；取样与写出都绑死画布尺寸。传放大尺寸进去 → 越界 + 行错位 → 空白。
所以 `StretchBlt` 和"compose 到放大尺寸"两条路都失败，根因同一个。

**正确做法：参数化布局。** 每个 UI 元素的位置/尺寸都要能从参数算出来：

```rust
struct Layout {
    zoom: f64,        // 用户缩放（0.6 .. 2.0）
    width: i32,       // 面板可用宽度（设计宽 × zoom）
    pad: i32,         // 内边距 = 12 * zoom
    row: i32,         // 行高   = 22 * zoom
    gap: i32,         // 间距   = 8  * zoom
    font_scale: f64,  // 字号 = 基准 * zoom
}
```

规则：
- 所有 rect 由 `Layout` 计算，禁止出现裸常量坐标
- 分区块（header / body / sep）高度都按 `zoom` 缩放
- 字体按 `zoom` 重新创建（不是放大位图）
- 面板高度变成 `zoom` 的函数，随之重算
- 命中测试用同一套 `Layout`，保证"看到的就是点得到的"

实现顺序（每步都要真机截图验证）：
1. 引入 `Layout`，先只让「操作」分区用它 → 缩放后截图对比
2. 逐个分区迁移
3. 迁移完成后把 `panel_zoom` 接进面板 UI（右下角 grip 拖动改 zoom）
4. 停靠站同样处理；停靠站还要先去掉点击穿透才能被用户拖动
