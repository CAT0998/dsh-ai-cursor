## 一、踩过的坑与规矩（每条都真机吃过亏）

### 1. 先看原始值，再派生
翻车两次：
- 面板高度不对，我从外部反推了两轮"是哪里多乘了一次"，其实只要打印 `draw_panel` 收到的 `h` 就能一眼看出。
- 停靠站滚轮缩放，我用 `(wParam>>16)&0xFFFF` 算出 delta=0 就下结论"没触发"，其实该先打印原始 `wParam`。

**规矩**：任何"我算出来的中间值不符合预期"时，第一步打印**上游原始值**，不要继续猜推导链。

### 2. 先证明诊断本身能用，再信它的结论
给 `draw_panel` 加日志后看到**零输出**，我据此判断"函数没被调用"，实际是日志插错了分支。
更早还把日志放在环境变量开关后面，环境变量根本没传进去。

**规矩**：加完诊断，先确认它**确实能在正常路径上打出东西**，再拿它当证据。

### 3. 测量前确认二进制是新的（2026-10-30 找到真凶）
**这次的根因**：`overlay/src/main.rs` 的 mtime 比编译产物还旧，cargo 判定"源码没变"，
直接跳过编译、把旧产物硬链回去，还打印 `Finished in 0.16s`。
于是连续好几轮的改动**根本没被编译**，包括"黑边怎么改都不变""高度 208 vs 252"。

规矩：
- 改完源码先 `touch -d "2030-01-01" overlay/src/*.rs`（把 mtime 推到未来）
- 编译**必须看耗时**：`Finished in 0.1x s` 基本等于没编；真编要 1~2 分钟（lto + codegen-units=1）
- 编译后用 `md5sum` 对比新旧产物哈希，哈希变了才算新二进制
- 日志里核对 `dock resize ...` 之类**能被新代码改变的具体数值**

### 3b. 测量前确认二进制是新的（原始记录）
面板高度"534 不对"查了很久，最后发现量的是**旧 exe**。

**规矩**：改完必须 `cargo build` → `cp` → 重启进程，再测。日志里有 `=== start pid=N ===` 可以核对是不是新进程。

### 3c. 日志被多个进程共用
`bin/logs/overlay.log` 是**按 exe 目录**开的，插件拉起的浮层、我手动起的 `--dock` 测试进程
都会写同一个文件，日志会交错。排查时先看 `args=[...]` 那行确认是哪个进程。

### 3d. 浮层进程不能写 `~/.dsh/ai-mouse-assets`
`std::fs::write` 到资产目录返回 **os error 5（拒绝访问）**，而同一个目录用 shell 写是成功的。
浮层能写的只有**自己 exe 所在目录**（日志就在那儿）。
所以跨进程的通信用 `<exeDir>/logs/dock-command.json`，不要用 assetDir。

### 3e. 托盘图标：Shell_NotifyIconW 返回 false + err=5
实测（本机，进程以管理员运行）：
```
tray icon added: false err=5 hwnd=HWND(0xd0716) hicon=HICON(0x1002b) cbsize=976
```
句柄、图标、结构体大小都正确，仍然 ACCESS_DENIED。explorer.exe 以普通级别运行，
我们的进程是管理员（`net session` 通过）。这是**同一家族**的第三个平台怪象：
`CreateWindowExW` 新类返回 null、`GetWindowTextW` 跨进程挂死、现在 `Shell_NotifyIcon` 被拒。

下一步可选：
1. 用一个**非提权**的辅助进程只挂托盘图标（需要 `ShellExecuteW` runas=false 启动）
2. 放弃托盘，改用停靠站/小地图表示"正在运行"（已具备）
3. 继续查：确认窗口是否与 explorer 在同一 window station/desktop

### 3f. 小地图三条（2026-10-30 修）
1. **不可拖动**：重画循环每 200ms 调 `present(..., Some(POINT{MAP_X, MAP_Y}))`，
   把窗口拽回常量位置——拖动其实是生效的，只是立刻被弹回。改用 `MAP_POS` 原子量。
2. **不可交互**：`if !dock { WS_EX_TRANSPARENT }` 把光标和小地图一起设成点击穿透。
   改成 `dock || MAP_MODE` 时才可交互。
3. **看不见内容**：桌面框 `0x2A3542`、窗口块 `0x1D2733` 压在 `0x0B1016` 上几乎无色差。
   改为填 `0x141C26` + 描边 `0x4A637D`，窗口块 `0x2E4159` + 描边 `0x3F5672`。

**遗留**：`--map` 进程有自己的 St，没人给它喂光标位置，所以蓝点永远在左上角。
要么让插件周期性 `move`，要么在小地图里读全局光标（`GetCursorPos` 更简单）。

### 3g. 两个测量陷阱（2026-11-05）
**① `GetProcessTimes` 的四个参数必须各用一个 FILETIME**
传同一个地址会恒读到 0，于是"证明"了 0% CPU。第一版就是这么把自己骗过去的。
测 CPU 的脚本一定要先用已知负载对一次（比如跑个忙循环，看读数是不是 100%）。

**② `git add -A` 会把正在干活的子代理的半成品一起提交**
`cd5f325` 那次我本想只提交花名册文档，结果把 `freeze-fix` 正在写的 439 行 main.rs 一起卷进去了。
**规矩：有子代理在跑时，只 `git add <具体文件>`，永远不要 `git add -A`。**

### 3h. `WH_MOUSE_LL` 在本机：装上但不回调（2026-11-05 复测）
```
hook_error=0   hook_handle=74188949   ← 安装成功
动真鼠标 + 真实点击后: hook_events=0  hook_ups=0   ← 一次都没触发
```
git 历史里 `05efa16` 就以 "installs, but never fires" 记过同一件事，**至今仍成立**。
排除了一个常见原因：消息泵用的是 `PeekMessage(hwnd=null, 0, 0, PM_REMOVE)`，
这是能收到钩子回调的正确写法，所以不是过滤问题。真实原因仍未定位。

**结论：不要基于全局低级钩子做功能。**
需要"AI 窗口只能被 AI 操作"时，改用 `EnableWindow(hwnd, FALSE)` + `PostMessage`
（窗口收不到任何真实输入，但程序化投递仍可达），系统原生、不用钩子。

### 4. `compose()` 只能产出画布自己的宽度
```rust
let stride_big = self.w * self.ss;   // 绑死画布尺寸
let i = (row + (ox*ss+sx)*4);        // 按索引取样 = 裁剪，不是缩放
let o = ((oy*self.w + ox)*4);        // 写出步长仍是 self.w
```
`w/h` 只是循环边界。传一个不同的宽度进去 = 越界写 → **空白**。
这就是"拉伸成品图"永远失败的根因，`StretchBlt` 和 `compose(放大尺寸)` 两条路都是同一个坑。

**规矩**：要缩放，**画布尺寸 = 输出尺寸**，几何在布局阶段就乘好。

### 5. 参数量化的功能，要在做功能之前先参数化
停靠站如果不是先做成"宽度由光标数算出来"，后面加 zoom 就会重复面板的翻车。

**规矩**：任何将来要乘缩放/数量因子的东西，先把几何写成函数，再谈功能。

### 6. 不要吞掉错误
`let _ = SetWindowPos(...)`、`.ok()`、`unwrap_or_else` 让失败完全不可见，
导致"命令被接受但没生效"这种状态查了很久。

**规矩**：至少记进日志；`GetLastError` 为 0 时说明信息无效，要换 windows crate 的 `e.code()`。

### 7. 补丁脚本必须断言，不能静默失败
多次出现"脚本打印成功但替换没匹配上"，最后编译报错才发现。原因包括：
搜索串里的 `\u{2039}` 转义 vs 文件里的字面字符 `‹`、heredoc 把 `\n` 变成真换行。

**规矩**：每个替换后 `assert`，或者跑完立刻 `grep` 复核关键标记。

### 8. 必须用真实鼠标验证，不能用协议模拟
面板开关那次，我用 `{"cmd":"toggle"}` 去"模拟点击"，根本没走窗口过程，
白测一轮还以为功能没做成。改用真鼠标点一次就通了。

**规矩**：UI 必须真点真拖真滚，坐标要**先截图确认**再点（我自己算错坐标好几次）。

### 9. `tsdown` 不做类型检查
`pnpm run build` 报"Build complete"但 `tsc --noEmit` 是红的，差点推上去。

**规矩**：每次提交前单独跑 `tsc --noEmit`。

### 9b. D3D11 三个坑（2026-10-31 小地图 GPU 化踩到）
1. **`Map` 只能用在 DYNAMIC 常量缓冲**：用 `D3D11_USAGE_DEFAULT` 建常量缓冲再 `Map(WRITE_DISCARD)`
   直接 `E_INVALIDARG (0x80070057)`。要 Map 就 DYNAMIC + `CPU_ACCESS_WRITE`，否则用 `UpdateSubresource`。
2. **staging 纹理的 `Map(DO_NOT_WAIT)` 在这个 Intel 驱动上照样阻塞 ~8ms**（1.4MB）。
   本机实测 `map=8172us`，不管有没有 `D3D11_MAP_FLAG_DO_NOT_WAIT`。
   **解法**：`CopyResource` 之后 `End(查询)`，下一帧先 `GetData` 轮询（它不阻塞），
   查到了才 `Map` —— 实测 `8172us → 11us`，同一份代码帧率还从 32fps 升到 44fps。
   教训：`DO_NOT_WAIT` 是"允许驱动不等待"，不是"保证驱动不等待"；要非阻塞必须自己拿查询做栅栏。
3. **WARP 设备 + 真实输出，`DuplicateOutput` 返回 `E_INVALIDARG` 而不是 `DXGI_ERROR_UNSUPPORTED`**。
   只认 UNSUPPORTED 会在某些驱动上一直重试而不降级。判"这台设备抓不了这个输出"要连
   `UNSUPPORTED / NOT_CURRENTLY_AVAILABLE / INVALID_CALL / E_INVALIDARG` 一起认。

### 9c. 先量每一段，再决定优化谁
本轮一开始"readback 6.5ms"是靠 `copy / map / rows` 三段分开计时才定位的：
`copy=3us map=8172us rows=191us` —— 一眼看出瓶颈在 Map，不在拷回内存。
**规矩**：GPU 异步管线的耗时，必须按阶段打点（main.rs 每 2s 打一行 `map stats`）。

### 10. 关键结论以日志为准
`bin/logs/overlay.log`：自动保存、512KB 轮转保留 5 份、`{cmd:"log_export",path}` 可导出。

### 11. 跨进程信箱文件不能把主循环 `continue` 掉（2026-11-01 修「点导出预设/保存当前卡死」）
现象：面板里点「保存当前 / 删除所选 / ＋新建栏」后，**整个面板当场不再重绘**，
进程 CPU 从 2.6% 跳到 **116%**（自旋，不是死锁），`dump` 命令 3s 超时且 BMP 不存在。

根因：主循环读 `<exeDir>/logs/dock-command.json` 的那段用 `if !fresh { continue; }`——
这里的 `continue` 是**主循环的**，跳过本帧剩余全部工作（重绘、resize、光标、以及
末尾 `sleep(8ms)`），于是每帧都从头再读同一个文件 → 永久卡住 + 100% CPU。
而面板写出的 `preset_save` / `preset_delete` / `toggle_column` **没带 `epoch`**，
读方 `epoch > started_ms` 恒假 → 一写成就是"过期命令"。文件是驻留的，
所以那个会话以及**之后每个进程**都一启动就是死的（停靠站/小地图同样中招，因为它们共用这段）。
删掉 `dock-command.json` 的瞬间同一个进程立刻恢复绘制——这是决定性证据。

规矩：
- **信箱文件 → 只跳过这条命令，绝不跳过帧**：用 `break 'label` 退出读取块，不要 `continue`。
- 每帧循环里每个 `continue` 后面都必须先 `sleep`，否则就是纯自旋（CPU 是判别死锁/自旋的第一指标）。
- 写跨进程命令**一律带 `epoch`**（`now_ms()`），读方按 `epoch > started_ms` 判新旧。
- 判"卡死"用 `{"cmd":"dump","target":"panel"}`：超时 3s 且文件不存在 = 主循环没走到绘制；
  单纯"日志没有新的 draw_panel"不能证明卡死（面板空闲时本来就不重绘）。
- 真鼠标点击前先确认目标在**屏幕上、且不在任务栏底下**：面板 1139 高时「预设」分区落在
  任务栏后面点不到，要先折叠「图案」把面板压矮再看坐标（坐标量错一次就会点到隔壁按钮）。

### 12. 面板重构（2026-11-01）踩到的四条

#### 12a `strip_prefix` 分支会吞掉同前缀的动作 id
`mt0..mt7`（菜单强调色色板）和 `mt_apply_0` / `mt_save`（动作）共用 `mt` 前缀。
写成 `if let Some(rest) = id.strip_prefix("mt") { … } else if id == "mt_save" { … }`，
后半截**永远进不去**（面板上按钮点了没反应，但色板是好的）。
**规矩**：前缀重叠时先解析出后缀，解析失败才落到动作分支：
```rust
let swatch = id.strip_prefix("mt").and_then(|r| r.parse::<usize>().ok());
if let Some(i) = swatch { … } else if let Some(rest) = id.strip_prefix("mt_apply_") { … }
```
这类 bug 编译器不会报，只能靠 **真点一次** 发现。

#### 12b 视口外的 Hit 必须"彻底不响应"，不是"不绘制"
滚动之后，滚出表头的按钮命中框仍然在那儿。绘图可以靠 `IntersectClipRect` 裁掉，
但**点击/悬停必须单独拦**：`pick()` 里对非表头控件要求"点落在视口内"。
验证方法（`scripts/live-panel-check.py` 的 A7/A8）：找一个被表头盖住一半的分区表头，
**点它那不可见的一半**，断言内容高度没变。用分区表头是因为它安全（不是"退出"）。

#### 12c 共享桌面上的真机测试要"重试到状态成立"，不要断言绝对像素
本机同时有别人/别的 agent 在动鼠标滚轮，绝对 `scroll` 值和"读矩形到落点之间"的
面板位置都可能变。`scripts/live-panel-check.py` 的做法：
- 目标用 `hits` 命令按 **id** 定位，不写死坐标；
- 每次点击前重读矩形，点完断言**状态**（`content_h`、`status.color`…），不对就重试，
  成立即停（避免把开关点两次）；
- 滚轮只断言方向/夹紧，不断言"正好 60px"。

#### 12d 注入滚轮：先怀疑注入，再怀疑窗口
`SendInput` 手写 `INPUT` 结构体在 x64 上很容易 cbSize 写错，失败时**返回 0 且没有报错**，
现象和"窗口收不到滚轮"一模一样。用 `mouse_event(MOUSEEVENTF_WHEEL, …)` 一次就通，
日志立刻出现 `panel wheel raw=0xFF880000 … delta=-120`。
**规矩**：凡"输入没反应"，先证明**输入真的发出去了**（返回值/原始 wParam 日志），
再怀疑被控窗口。

#### 12e 面板进程读宿主写的文件：低频重读，不要每帧读盘
`menu-themes.json` / `cursor-presets.json` 是宿主写的，面板只能读。`view_of()` 每帧被调
好几次，放在里面读盘会拖慢绘制。做法：主循环里 1.5s 一次 `refresh_panel_lists(&mut st)`
（面板隐藏时直接跳过），`view_of` 保持纯函数。

### 13. 面板窗口化（2026-11-01）踩到的三条

#### 13a 控件“存在但看不见”＝画在了裁剪之后
标题栏 `AI 鼠标` / `─` / `✕` 在 `panel_layout` 里、`hits` 也能查到、点也能点，
但屏幕上没有。根因是 `draw_panel` 先 `IntersectClipRect(HEADER_BOTTOM..)` 再统一遍历
`hits` 画，而标题栏控件的矩形整个在 `HEADER_BOTTOM` 之上 → 被裁掉。
**规矩**：**先画固定 chrome（标题栏），再设滚动裁剪，画完 `SelectClipRgn(NULL)` 恢复**；
“控件在模型里” 不等于 “像素在屏幕上”，视觉类改动必须看 dump 帧。

#### 13b 分层窗口逐像素命中：alpha=0 的像素点击直接穿透
Windows 对 `WS_EX_LAYERED` + `UpdateLayeredWindow` 的窗口做**逐像素**命中测试，
alpha=0 的像素点在它上面等于点桌面。所以圆角外侧的四角**永远收不到 `WM_LBUTTONDOWN`，
拖右下角改大小的热区等于不存在（日志里连 `resize start` 都没有）。
**规矩**：需要点击/拖动的热区，底下必须有**不透明**像素；圆角窗口要在边框带先铺一层
不透明底色，再画圆角机身。验证方式：`WindowFromPoint` 看那个点落到了哪个窗口。

#### 13c 超采样画布上的 `GetTextExtent` 是 2× 像素
字体按 `-pt * ss` 建、在 `ss` 倍的 DC 上量宽度，`ext.cx` 自然是超采样像素；调用方却
把它当设计像素用（`x = right - tw`），于是所有居中/右对齐文字都**左偏半个字宽**。
短 ASCII 标签看不出来（`#4FC3F7` 只偏 40px 里的一点点），长中文署名一画就穿帮：
文字整块跑到标题栏中间。
**规矩**：`Canvas::text_w()` 这类“测量”函数必须返回**调用方的单位**（这里除以 `ss`），
单位混淆的 bug 只在长文本/大字号上暴露，别靠肉眼验收。

### 14. 滚动条 / 流体布局（2026-11-05）踩到的四条

#### 14a 「流体」和「缩放」差在一个乘号
用户否定的是"整体放大字体+间距"，要的是"同一批控件重新分配横向空间"。
所以流体布局里**只能动 x/w，不许动字体号、行高、控件高度**。
可执行的判据：同样状态、452 与 700 两个宽度各 dump 一帧，**标题区域的像素必须逐点相同**
（`H6d`）。写任何 `w * k` 之前先问：这个 k 会不会也乘到字体上？

#### 14b 滚动条手柄和改大小热区会互相偷事件
边框热区是"窗口边缘 6px"，而滚动条天然贴着边缘画——两者重叠时，按下先命中谁就成了
产品问题（用户会看到"拖滚动条变成了改窗口大小"）。解法不是加大热区，而是**分层**：
滚动条的 rect 由几何统一算、鼠标按下的判定顺序固定成 `滚动条 → 边框 → 控件`，
再把滚动条画在边框带**里面**（`panel_w-10`、离底 7~13px），两边互不吃。
另外 3px 的细条看着好、点着差：抓取区单独放大 4px，但**只往内容侧放**（往边缘放又会抢边框）。

#### 14c 断言"某个动作写了日志"要能扛日志轮转
面板日志 512KB 轮转，而验收脚本用"记下 offset，读之后新增的字节"来判断点击有没有生效。
轮转一发生，`seek(offset)` 直接越过 EOF，**真的写过的动作也会判成没写**——表现为随机失败。
规矩：读之前先比较文件大小，比 offset 小就说明轮转过、整份新文件都算"新增"；
再兜底看一眼轮转前的 `overlay.1.log` 尾部。顺带把每帧一行的 `TRACE draw_panel` 删了：
一次 5 分钟验收能写 400KB，本身就是在制造轮转。

#### 14d 共享桌面上的面板测试要和"在跑的宿主"共存
宿主每 250ms 排空一次 `dock-command.json`，脚本点完 0.4s 再读信箱经常读空。
判据改成"信箱里还有 **或** 面板日志里新增了这条意图"，两者任一成立即可；
点完立刻重读太脆，靠日志尾部才是稳的。
